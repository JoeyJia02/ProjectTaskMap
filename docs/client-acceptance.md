# 客户端验收与失败审批修复

## 最新使用确认（2026-10-16）

用户在项目会话中确认：客户端验收已经完成，并已在多个实际项目中使用。该项为用户报告的真实使用结果；具体项目数量、使用时长和各验收步骤的逐项记录未提供，不据此推定所有环境或长时场景均已覆盖。下文保留此前的故障分析和验收步骤，作为历史记录及后续回归依据。

2026-09-28：用户确认认证恢复后地图看起来正常；同时报告原来 1 条待审提案，连续批准六次后变成 7 条。

根因：review 把批准转换为新的 manual delta，复用 applyInside；后者把执行失败存成新 conflict。每次审批生成新 timestamp，因此不能去重，且原提案一直 pending。

修复：审批失败事务回滚，返回明确 409，不创建冲突、历史或版本；已成功处理的 review 仍可幂等重试。UI 预检整个操作集合，不给无法应用的提案提供批准按钮。历史失败副本仅在 source=manual、request key/evidence 指向原审批且操作集合相同的情况下合并展示。用户处理原提案后关联副本标记为 rejected，保留审计记录；独立提案不合并。

验证：npm run check 100 项通过；新增浏览器测试在隔离项目中验证六次失败不增项、保留当前不改任务、有效审批正确更新一次。业务项目中的历史提案尚未代用户处理。

## 真实客户端最短验收

1. 在目标业务项目的 Parking Lot 输入一条带日期的“验收用想法”，回车保存，确认成功和版本变化。记录其内容，不拿真实任务做破坏性测试。
2. 关闭地图后在原会话重新打开，确认想法仍在。点击“刷新项目地图”核对进度，确认不会重复创建该想法或已完成任务。
3. 在另一个会话用同一 bindingKey 打开同一项目，确认项目 ID、版本和想法一致；修改该测试想法的说明，回到原会话，等待一次自动读取，核对内容一致。不要把另一个业务项目绑定到开发项目的 key。
4. 对无法应用的提案，确认说明明确且没有批准入口；有效提案批准后待审数减少、版本只增长一次。历史失败副本合并展示后，用户决定保留当前可将原提案和这些副本一起归档。
5. 宿主后台放置超过一小时后恢复，确认仍可读取并编辑同一测试想法。断网后应保留快照，恢复网络后应重新读取。

只有上述客户端结果得到确认，才完成真实客户端验收；协议测试和短时正常不替代跨会话、长时恢复证据。
